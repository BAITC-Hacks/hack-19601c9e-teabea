# Граф денег — восстановление структуры организованной группы

```
graf_deneg/
├── pipeline.py          граф → метрики → роли → кластеры → приоритеты → 3 CSV
├── app.py                Streamlit-экран просмотра
├── convert.py             parquet → csv без pyarrow (свой парсер, см. ниже)
├── pqmini/                мини-парсер parquet (thrift compact + ZSTD через ctypes)
├── requirements.txt
├── data_parquet/          исходные .parquet из ТЗ + README датасета
├── data/                  сконвертированные .csv (готовы к pipeline.py)
└── out/                   готовые выгрузки: nodes_roles.csv, clusters.csv, top_nodes.csv
```


Инструмент по сети внутрибанковских переводов (2248 узлов, 3119 рёбер, 4-хоповый обход
от 81 seed-клиента) присваивает каждому узлу объяснимую роль, разбивает сеть на кластеры
и строит приоритетный список для проверки аналитиком.

## 1. Как запустить

```bash
pip install pandas numpy networkx pyvis streamlit

# 1) граф -> метрики -> роли -> кластеры -> приоритеты -> 3 CSV (< 5 секунд)
python3 pipeline.py --data ./data --out ./out

# 2) экран просмотра
streamlit run app.py -- --data ./out --edges ./data/edges.csv
```

`./data/` содержит `nodes.csv`, `edges.csv`, `transactions.csv` (та же схема, что в
`nodes.parquet` / `edges.parquet` / `transactions.parquet` из ТЗ — при наличии `pyarrow`
их можно читать напрямую через `pd.read_parquet`, скрипт агностичен к формату).

Если под рукой только сырые `.parquet` и нет `pyarrow`/сети (например, в изолированном
контейнере) — есть `convert.py`, конвертер на чистом Python без единой сторонней
зависимости (свой парсер thrift/parquet, ZSTD через системную `libzstd.so.1`):

```bash
python3 convert.py --in ./data_parquet --out ./data
```

Даёт побайтово идентичный результат `pd.read_parquet` (проверено на исходных файлах кейса).
Если `pyarrow` есть — `convert.py` не нужен, просто положите `*.csv` в `./data/` сами
(`pd.read_parquet(...).to_csv(...)`) или адаптируйте `load()` в `pipeline.py` под
`pd.read_parquet` напрямую.

## 2. Критерии ролей и пороги

Роль назначается функцией `assign_role()` строгой иерархией if/elif (порядок проверки
важен — см. докстринг в `pipeline.py`). Пороги калибруются автоматически по квантилям
фактического распределения метрик (`compute_thresholds()`), а не захардкожены:

| Роль | Правило | Порог в этом прогоне |
|---|---|---|
| **coordinator** | ≥2 прямых соседа — seed-клиенты, ИЛИ узел — точка сочленения графа с высокой betweenness | `n_seed_neighbors≥2` или `is_articulation & betweenness≥0.0015` (95-й перцентиль) |
| **consolidator** | получает от многих плательщиков больше, чем отдаёт | `in_deg≥5` (90-й перцентиль по узлам с in_deg>0, не ниже 5) и `in_deg>out_deg` |
| **distributor** | веерно раздаёт многим больше, чем получает | `out_deg≥15` (90-й перцентиль, не ниже 15) и `out_deg>in_deg` |
| **transit** | пропускает почти всё, что получил | `0.8≤pass_through≤1.2`, оба потока `>0`; **не применяется к seed-узлам** (см. ограничение №2) |
| **terminal** | реальный конечный получатель | `out_deg=0` и `depth<4` (обход дошёл до настоящего конца, не был обрублен) |
| **peripheral** | ничего выраженного не выявлено, включая неподтверждённые frontier-узлы | всё остальное, в т.ч. `out_deg=0 & depth=4` без сильного `in_deg` |

Проверка условий идёт сверху вниз: coordinator → consolidator → distributor → transit →
terminal/peripheral. Пример: узел с 30 плательщиками, который также соединяет двух seed —
получит `coordinator`, а не `consolidator`, потому что структурная роль моста важнее
локального объёма (обоснование — узел такого типа кандидат в организаторы независимо от
собственного оборота).

Порог для `betweenness` считается как вес пути `1/sum_kzt` — крупный перевод трактуется
как «более вероятный» маршрут денег (короче путь), что делает метрику осмысленной именно
для денежного графа, а не для количества переводов.

## 3. Ловушка «444 узла на 4-м колене без исходящих»

Наивное правило `out_deg=0 ⇒ terminal` дало бы 444 ложных срабатывания. Решение:
- `is_frontier_cutoff = (depth==4) & (out_deg==0)` — помечает подозрительные узлы отдельно;
- **настоящий terminal** присваивается только если `depth<4` (обход не мог продолжиться
  из-за реального отсутствия исходящих, а не из-за лимита глубины) — таких узлов **1092**;
- из 444 frontier-узлов **0** получили `consolidator` (ни у одного нет достаточного `in_deg`
  для этого в текущих данных) — все ушли в `peripheral` с явной пометкой в `evidence`, что
  это неподтверждённый обрыв обхода, а не факт «деньги осели»;
- ещё 18 узлов с `depth<4 & out_deg=0` получили не `terminal`, а `coordinator`(10) или
  `consolidator`(8) — потому что структурные/аккумулирующие признаки сработали раньше
  терминальной проверки в иерархии (это осознанное решение, не ошибка).

## 4. Что на выходе

**`nodes_roles.csv`** (2248 строк, без пропусков):
`gid, role, role_score, cluster_id, priority_score, evidence`

**`clusters.csv`** (89 кластеров, Louvain на неориентированной проекции, вес = сумма KZT):
`cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`

**`top_nodes.csv`** (40 строк, отсортировано по приоритету):
`rank, gid, role, priority_score, why`

Приоритет: `0.40·(вес_роли·role_score) + 0.25·log-норм.объём_входящих + 0.20·norm(betweenness)
+ 0.15·norm(число seed-соседей)`. Вес роли: coordinator 1.0, consolidator 0.9, distributor
0.75, transit 0.35, terminal 0.25, peripheral 0.10 — формула явная, без ML-моделей.

Дополнительно пишется `node_metrics_full.csv` — все посчитанные метрики по всем узлам,
для отладки и для фронтенда.

## 6. Ограничения подхода

- **Входящие потоки извне выборки не видны.** Граф собран ОТ 81 seed-клиента только по
  исходящим переводам. Всё, что seed получили извне этой выборки, в данных отсутствует.
- **`in_kzt` у seed-узлов занижен** ровно из-за предыдущего пункта — поэтому правило
  `transit` (pass_through≈1) намеренно не применяется к seed-узлам: у них соотношение
  «отдал/получил» может быть искусственно >20 и не отражает реального поведения.
- **444 узла на 4-м колене без исходящих — не обязательно terminal.** Это может быть как
  реальный конец цепочки, так и просто предел глубины обхода. Подход помечает такие узлы
  явно и не присваивает им уверенный `terminal` (см. раздел 3).
- **Порог 5000 KZT скрывает дробление сумм.** Серии переводов чуть ниже порога, которыми
  могли раздробить крупную сумму, не попали в выгрузку — реальный объём консолидаторов/
  дистрибьюторов может быть выше видимого.
- **Сеть не монолитна** — 35 слабосвязных компонент, включая 19 полностью изолированных
  узлов; кластеризация Louvain разбивает их ещё мельче (89 кластеров) — для маленьких
  компонент из 2–5 узлов это, по сути, тот же компонент, что и слабо-связная компонента.
- **Betweenness и articulation points посчитаны на разных представлениях графа**:
  betweenness — на направленном графе с весом `1/sum_kzt`; articulation points — на
  неориентированной проекции (иначе понятие «точки сочленения» для направленного графа
  плохо определено). Это указано явно, как и просит ловушка №4 из ТЗ.

## 7. Масштабирование до ~1 млн узлов

Без реализации, только направление:
- **Инкрементальные обновления графа** вместо полного пересчёта: при появлении новых
  переводов пересчитывать метрики только для затронутых узлов и их k-hop окружения, а не
  весь граф заново.
- **Приближённый betweenness** (`k`-sampling, как уже заложено в коде при `n_nodes>3000`)
  вместо точного алгоритма Brandes, который на 1M узлов не завершится за разумное время.
- **Graph DB** (Neo4j / JanusGraph / Memgraph) вместо графа в оперативной памяти —
  запросы на пересечение соседей, k-hop окружение и агрегаты по времени делаются нативно,
  без выгрузки всего графа в Python.
- **Батчевая кластеризация**: Louvain на графе такого размера всё ещё применим, но лучше
  запускать на распределённом движке (GraphFrames поверх Spark) с ограничением по времени
  сходимости, либо на сэмплированной/загрублённой (coarsened) версии графа.
- **Инкрементальный скоринг приоритета**: пересчитывать `priority_score` не для всех узлов,
  а только для тех, чьи входные метрики (in_deg/out_deg/betweenness/cluster) изменились
  с прошлого прогона — держать материализованную витрину метрик, обновляемую triggers'ами.
