# Полный промпт для бэкенда

Ты дорабатываешь существующий проект «Граф денег» в открытой папке VS Code. Прочитай AUDIT.md, 04_CONTRACT.md, source/task.txt и pipeline.py. Реализуй исправления в файлах, запусти расчёт и проверки. Не ограничивайся объяснением и не переписывай проект с нуля. app.py делает другой участник: соблюдай файловый контракт.

## 1. Вход и воспроизводимость

Добавь чтение трёх исходных parquet через pandas/pyarrow в pipeline.load. CSV оставь дополнительным режимом, с явной проверкой полного набора входных файлов. Главная команда: `python pipeline.py --data data_parquet --out out`. Она должна без ручной конвертации создавать три обязательных CSV, node_metrics_full.csv, run_metadata.json и совместимый data/edges.csv. Предусмотри --edges-export. Относительные default-пути вычисляй от файла проекта, явно переданные CLI пути — обычным предсказуемым способом.

pqmini не импортировать на основном пути. Его Linux-парсер не нужен для Windows-сценария. Не удаляй оригинал, но не делай неподтверждённых заявлений о поддержке произвольного parquet. requirements-core.txt: pandas, numpy, networkx, scipy, pyarrow и необходимые тестовые зависимости в отдельном dev-файле по необходимости. Фиксируй действительно проверенные версии; не объявляй проверенным окружение, которое не запускал. Удалять HITS можно, если он не влияет на роли/приоритет; это избыточная метрика в текущем алгоритме.

## 2. Валидация

Проверь схемы, типы, уникальность nodes.gid и пар edges, существование endpoints, конечные неотрицательные суммы, положительные целые n_tx, даты и depth. Пересчитай transactions по (src,dst), сравни пары, суммы с явным денежным допуском и количества точно. Ошибки — ValueError/понятная диагностика и ненулевой exit code, не только assert, отключаемый python -O. Запрещено молча терять строки или заменять пропуски в идентификаторах.

Сохраняй int64 без float-перехода. Сверь actual counts с исходным описанием, но не хардкодь число строк в универсальном алгоритме.

## 3. Граф и метрики

Добавляй все nodes до рёбер. Сохраняй изоляты в неориентированной проекции. Направленные входы/выходы и PageRank остаются. Встречные суммы для Louvain уже складываются правильно — сохрани это. Обработай пустой граф и граф без рёбер. У изолятов отдельные кластеры; нумерация стабильна, random seed фиксирован, порядок входов нормализован.

Для betweenness выбери невзвешенный направленный вариант: он измеряет структурное посредничество. На исходном объёме замерь точный расчёт, при необходимости используй детерминированную аппроксимацию. Если сохраняешь 1/sum_kzt, документируй как допущение стоимости пути, без утверждения о вероятности движения денег. Не придумывай необходимость GPU.

## 4. Исправление ролей

Сохрани текущие шесть enum и общую объяснимую структуру правил. Пороги, границы и порядок вынеси в явную конфигурацию/таблицу в документации.

- ПЕРВЫМ обработай полностью изолированный узел: peripheral, evidence «Наблюдаемых переводов нет; данных для роли недостаточно», консервативный score. Ноль входящих никогда не делает узел terminal.
- terminal: только наблюдаемый положительный вход, out_deg=0, depth<4, не seed. Формулировка «возможный конечный получатель в наблюдаемой выборке». Даже такой узел не имеет доказанного полного баланса.
- transit: не seed, положительные вход/выход, не boundary, отношение в настроенном диапазоне. Убери утверждение «деньги не задерживаются»: месячные суммы сами этого не доказывают.
- consolidator: входящий веер по текущему квантильному порогу — допустимый структурный сигнал. На boundary сохраняй возможность этой роли, но не используй 0% выхода как доказательство удержания. Добавь предупреждение прямо в evidence. У seed отношение потоков не использовать для подтверждения удержания. Устрани недостижимую дублирующую ветку.
- distributor: исходящий веер; in_deg/out_deg — количества контрагентов, не сравнение сумм. Согласуй README с фактическим условием.
- coordinator: одной связи с двумя seed недостаточно. Сделай более строгую объяснимую гипотезу минимум по двум сигналам. Для простого MVP: n_seed_neighbors>=2 И положительная betweenness>=95-го перцентиля положительных значений. Артикуляцию можешь оставить как дополнительное объяснение, но не как вывод о виновности. Если положительных значений нет, правило отключено; нулевой порог не должен выделять нули. Если подходящих узлов нет — не подгонять результат ради наличия роли.
- Остальные peripheral; это «недостаточно выраженных признаков», не «безопасен».

Если роли пересекаются, явно сохрани приоритет coordinator → consolidator → distributor → transit → terminal → peripheral после ранней обработки изолятов. Сохраняй альтернативные сработавшие признаки в explanation. При изменении порядка объясни решение. Не фиксируй прежние 1092 terminal и 78 coordinator: распределение после исправления должно получаться из данных.

## 5. Приоритет и объяснения

Для минимальной доработки сохрани текущую формулу приоритета: 0.40*(вес роли*role_score)+0.25*minmax(log1p(in_kzt))+0.20*minmax(betweenness)+0.15*minmax(min(n_seed_neighbors,5)). Документируй ограничения, в том числе зависимость приоритета от эвристической роли. Нормализация константного признака даёт 0. Добавь четыре численных вклада priority_role/volume/bridge/seed, их сумма должна совпадать с priority_score в пределах округления.

role_score опиши по каждой роли; это не вероятность. Консервативно ограничь поддержку ролей, основанных на неполном наблюдении; правило ограничения зафиксируй в коде и README. Evidence 1–200 символов, реальные числа, важное ограничение не теряется при обрезке. Why объясняет именно приоритет и его главные вклады, а не только повторяет роль. explanation — полная версия.

В кластерах замени «явный организатор», «курьеры» на структурные гипотезы. top_gids выбирай после приоритизации по priority_score, при равенстве gid численно ASC. Раздели расчёт членства кластеров и оформление гипотез, если нужно избежать циклической зависимости.

## 6. Результаты и тесты

Следуй 04_CONTRACT.md. Сначала записывай комплект во временную директорию, валидируй его и только затем публикуй; UI не должен читать смесь старых/новых результатов. metadata со status=success публикуй последним. run.py будет запускать UI только после успешного завершения CLI.

Создай tests/test_pipeline.py: изолят, seed без выхода, boundary с большим входящим веером, транзит, консолидация, распределение, осторожный terminal, coordinator с двумя сигналами/без второго, отсутствие положительных betweenness, граф без рёбер, встречные веса, неверный n_tx, длинный gid. Тесты должны проверять смысл и инварианты, не точное старое распределение.

На настоящих parquet выполни пересчёт, проверь полное покрытие и уникальность gid, scores, evidence, cluster_id, топ не менее 20, сортировку и совпадение агрегатов. Повтори расчёт и сравни три обязательных CSV по содержимому; для равных scores нужен стабильный tie-break. Замерь весь путь от parquet до файлов: меньше 300 секунд. Сохрани реальную конфигурацию и длительность. Не заявляй accuracy без размеченных ролей.

В финале: созданные/исправленные файлы, команда запуска, фактический итог проверки, новое распределение ролей и все непроверенные пункты. Если зависимости недоступны, объясни блокировку и подготовь код без выдуманного успешного прогона.
